Мини-приложение в Телеграме для пары: вместо ссылок и скриншотов, разбросанных по переписке, один общий список желаний. Каждый добавляет свои хотелки, видит хотелки второго и понимает, что подарить или куда сходить. Открывается прямо в Телеграме, без установки, изменения второго человека появляются сразу.

Одной фразой для резюме: мини-приложение Телеграма на чистом JavaScript и Supabase с обновлением в реальном времени, экранированием пользовательских данных и тестами на Node.

## Что умеет

- **Четыре категории**: подарки, рестораны, места и мелкие радости. У каждой свои поля: у подарка уровень желания, у ресторана и места ссылка на карту, у ресторана средний чек.
- **Моё и её**: переключатель между общим списком, своими желаниями и желаниями второго. Править и удалять можно только свои записи.
- **Уровень желания** от одного огонька до «безумно хочу», самые желанные подсвечиваются.
- **Отметка «сделано»**: исполненное желание остаётся в списке приглушённым, его видно, но оно не мешает.
- **Фото, цена и ссылка** на товар, чтобы не искать заново.
- **Живое обновление**: если второй человек добавил или поменял запись, список обновится сам.
- **Свайп** влево и вправо переключает категории, тёмная тема под оформление Телеграма.

## Как устроено

Одностраничное приложение без сборки. Разметка на Tailwind, логика на чистом JavaScript, данные в таблице `items` в Supabase. Скрипт Телеграма для мини-приложений отдаёт имя пользователя и управляет вибрацией и цветом шапки.

```
index.html          разметка и модальные окна
config.js           адрес и публичный ключ Supabase (пример: config.example.js)
lib.js              чистые функции: экранирование, проверка ссылок, фильтр, разметка карточки
script.js           работа с базой, обработчики кнопок, модальные окна, свайпы
style.css           цвета, карточки, эффект стекла
test/lib.test.js    тесты для lib.js
```

Почему так:

- **Без сборки и фреймворка.** Приложение маленькое, а GitHub Pages отдаёт статику бесплатно. Ради пяти экранов тянуть сборщик и React было бы лишним.
- **Supabase вместо своего сервера.** База, хранение и подписка на изменения в реальном времени есть из коробки, а своего сервера нет вовсе. Цена за это: вся защита данных держится на правилах доступа в самой базе (см. ниже).
- **Логика отрисовки отдельно от работы с базой.** В `lib.js` нет ни Supabase, ни Телеграма, поэтому его можно проверять тестами в Node без браузера.

## Запуск

1. Создайте проект в Supabase и таблицу `items` с полями `id`, `created_at`, `title`, `category`, `added_by`, `price`, `link`, `location`, `desire_level`, `image_url`, `is_completed`. Для живого обновления включите Realtime для этой таблицы.
2. Скопируйте `config.example.js` в `config.js` и впишите адрес проекта и публичный ключ (Project Settings → API).
3. Положите файлы на любой статичный хостинг, например GitHub Pages.
4. В BotFather укажите этот адрес как мини-приложение своего бота.

В обычном браузере приложение тоже открывается, но имя пользователя берётся из Телеграма, поэтому вне его новые записи подписываются как «Я», а вибрация не работает.

## Про ключ в config.js

В `config.js` лежит публичный ключ Supabase (`sb_publishable_...`). Он не секрет: браузер всё равно получает его при загрузке страницы. Поэтому данные защищает не ключ, а правила доступа (Row Level Security) в самой базе. Если их не включить, любой, кто открыл страницу, сможет читать, менять и удалять все записи. Секретный ключ (`service_role`, `sb_secret_...`) в код приложения класть нельзя никогда.

## Тесты

```
npm test
```

Нужен только Node 18 или новее, зависимостей нет. Тесты проверяют, что название, цена, ссылки и id из базы не могут превратиться в код на странице, что ссылки `javascript:` отбрасываются, что кнопки правки и удаления есть только у своих записей, что фильтр «моё/её» и уровни желания работают. На каждый push в main тесты запускаются на Гитхабе.

## Что было непросто

**Данные второго человека попадали в разметку как код.** Раньше карточка передавала всю запись прямо в `onclick="viewItem({...})"`, а название и цена вставлялись в HTML как есть. Достаточно было второму человеку назвать подарок `<img src=x onerror=...>`, и этот код выполнился бы у первого. В браузере это проверено: на старой версии такой подарок запускал код и ломал весь список. Теперь всё, что пришло из базы, проходит через `escapeHtml`, ссылки открываются только если начинаются с `http` или `https`, а кнопки знают лишь `data-id`. Один общий обработчик на весь список находит запись в памяти по id и решает, что делать.

**Фото без отдельного хранилища.** Картинка читается в браузере как base64 и сохраняется прямо в строке таблицы. Так проще: одна таблица, один запрос, никаких прав на хранилище. Минус в том, что большие фото раздувают таблицу и каждый запрос списка. Для двоих это терпимо, для большего числа людей нужно переносить фото в Supabase Storage.

**Разные поля для разных категорий.** Вместо четырёх форм одна, которая показывает и прячет поля в зависимости от категории. Подпись к цене тоже меняется: у ресторана это средний чек, у места просто стоимость, если она есть.

## Что можно улучшить

- Различать людей по номеру пользователя Телеграма, а не по имени. Сейчас двое с одинаковым именем сольются в одного, а подпись «Её» зашита для пары.
- Готовый SQL с правилами доступа для Supabase прямо в репозитории.
- Перенести фото в Supabase Storage и сжимать их перед загрузкой.
- Напоминания о днях рождения и годовщинах, общий бюджет списка.
